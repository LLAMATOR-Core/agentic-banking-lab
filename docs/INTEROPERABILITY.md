# MCP и A2A

Контракты банка, партнёра и памяти. Состав систем описан в
[ARCHITECTURE.md](ARCHITECTURE.md), ограничения защиты в [SECURITY.md](SECURITY.md).
Задания по замене участников и проверке совместимости: [COURSE_PLAN.md](COURSE_PLAN.md).

## Участники и протоколы

| Связь | Контракт | Ответственность |
|---|---|---|
| UI → банковский микросервис | `POST /v1/chat`, пользовательский JWT | Аутентификация клиента и единый ответ |
| Оркестратор → выбранные агенты | Локальный Python-вызов, внутренняя схема `SkillTask` | Выбор и дополнительные вызовы; итоговый ответ готовит оркестратор |
| Агент → общий MCP → АБС при `secure` | MCP и REST АБС, два Token Exchange | Учётная запись агента, scope, инструмент, ресурс и клиент |
| Агент → уязвимый MCP → АБС при `vulnerable` | MCP с `customer_id` из ответа LLM и пользовательским JWT | MCP не сверяет ID с токеном; АБС доверяет сервисному заголовку |
| Тревел-агент банка → внешний партнёр | A2A 1.0 через `travel-api` | Параметры поездки и собственный сервисный JWT `travel-skill` |
| Каждый агент → память | `/api/v1/skills/*`, собственный обмен JWT с `memory.access` | Серверная привязка клиента, области и автора |

`operations-skill`, `investment-skill`, `travel-skill` обозначают OAuth-клиентов
одного банковского процесса. Между системами используются MCP, A2A и API памяти;
`SkillTask` описывает локальный вызов.

## OAuth2 и Token Exchange

При `ABS_MCP_MODE=secure` для портфеля выполняются два обмена в Keycloak 26.7.4:

| Кто обменивает | Исходный токен | Новый `aud` | Новый `azp` | Scope |
|---|---|---|---|---|
| `investment-skill` внутри банка | JWT пользователя `bank-ui` | `bank-mcp` | `investment-skill` | `portfolio.read` |
| Общий защищённый MCP | Токен инвестиционного агента | `abs-api` | `bank-mcp` | `portfolio.read` |

Локальный оркестратор не выполняет обмен для вызова агента. Каждому агенту доступны
собственные `client_id`/секрет в его клиенте авторизации. Исходный пользовательский
JWT используется для Token Exchange внутри сервиса и не передаётся защищённому MCP
или памяти. При `vulnerable` тот же JWT предъявляется уязвимому MCP напрямую.
`bank-ui` включает идентичности трёх агентов в audience, чтобы Keycloak разрешал
соответствующему клиенту обмен предъявленного пользовательского токена.

Обмен использует `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`,
`subject_token_type=urn:ietf:params:oauth:token-type:access_token`,
`requested_token_type=urn:ietf:params:oauth:token-type:access_token`,
`subject_token`, `audience`, `scope` и аутентификацию клиента.
`customer_id` переносится из атрибута пользователя; получатель проверяет подпись,
issuer, срок, `azp`, `aud` и scope. Банковский аналитик получает пять разрешений чтения;
MCP при каждом вызове обменивает токен только на scope конкретного ресурса.

| Клиент Keycloak | Назначенные optional scopes |
|---|---|
| `operations-skill` | `customer.read`, `accounts.read`, `operations.read`, `portfolio.read`, `products.read`, `memory.access` |
| `investment-skill` | `portfolio.read`, `memory.access` |
| `travel-skill` | `travel.plan`, `memory.access` |
| `bank-mcp` | `customer.read`, `accounts.read`, `operations.read`, `portfolio.read`, `products.read`, `bank.write` |

Широкий набор у `bank-mcp` нужен общему серверу, включая dashboard и прежний граф.
Он обменивает токен только на scope выбранного ресурса. Агент с узким токеном
не получает этот широкий набор: MCP проверяет его учётную запись и требуемый scope,
АБС повторяет проверку ресурса.

К памяти каждый агент выполняет свой обмен: `aud=memory-service`, `scope=memory.access`.
Тревел-агент получает сервисный JWT `travel-skill`, `aud=travel-agent`, `travel.plan`;
инвестиционный агент использует свой сервисный JWT для поиска.
Исходный банковский JWT партнёру не передаётся.

`audience` фильтрует назначения, `scope` выбирает разрешённые клиенту optional scopes
и может расширять их относительно исходного токена. Ограничение задают назначения
каждому клиенту и проверки получателя. `operations.read` инвестиционному клиенту
не назначен. Ответ обмена без требуемого scope отклоняется.
[Источник закреплённой версии](https://github.com/keycloak/keycloak/blob/26.7.4/docs/guides/securing-apps/token-exchange.adoc).

Пользовательские токены не кэшируются между обменами, сервисные кэшируются отдельно
в объектах агентов. При ошибке обмена запрос завершается без подстановки широкого
токена. Секреты всех агентов находятся в одном процессе и раскрываются при его
компрометации.

`get_account_statement` требует `operations.read` и вызывает
`GET /internal/statement` с фильтрами счёта и включительного периода, лимитом
и смещением. АБС проверяет владельца счёта. Ответ содержит операции, текущие
остатки, число записей, `has_more` и итоги завершённых операций по валютам.
Денежные инструменты требуют `bank.write`, которого нет у обоих аналитических агентов.

Внешний `travel-agent` выполняет веб-поиск через собственный
`travel-duckduckgo-mcp` с `azp=travel-agent`, `aud=travel-duckduckgo-mcp`.
Он возвращает рекомендации и ссылки через A2A;
его поиск и трассы остаются в системе партнёра.

## Внутренняя схема задачи

`SkillTask` передаётся локально: `message`, `conversation_id`, `experiment`
с `experiment_id`/`run_id` и необязательный `travel`. Лишние поля запрещены схемой.
Клиент и JWT поступают отдельными серверными аргументами из проверенного запроса,
а не из LLM. Внутреннего `POST /v1/task` нет.

Внутренний ответ исполнителя содержит `response`, `data`, `tool_calls` и
`requires_confirmation=false`. В `data.experiment` находятся режим памяти, ID извлечений,
кандидатов и метки опыта. Уточнение поездки возвращает `missing_fields` и вопрос.
Оркестратор использует ответы для выбора следующего агента или итоговой генерации.
`data.agent_results` сохраняет ответы исполнителей по их именам,
`data.orchestration.delegated_agents` перечисляет вызванных. `intent` и данные
верхнего уровня относятся к первому исполнителю; без вызовов `intent=general`.
Внешний `/v1/chat` преобразует итоговый `response` в `message`.
Денежные задачи оркестратора отклоняются с `409`; нарушение схемы возвращает `422`.
Вызываемый сервис возвращает `401` при неверном JWT и `403` при запрещённом клиенте,
назначении или scope.
HTTP 200 у JSON-RPC может содержать ошибку инструмента.

## MCP-серверы

Собственные серверы предоставляют `POST /mcp` с версией протокола `2025-06-18`.
Поддерживаются `initialize`, `notifications/initialized`, `tools/list` и `tools/call`.
Клиент выполняет инициализацию, понимает JSON и SSE, сохраняет `Mcp-Session-Id`, если
сервер выдал идентификатор сессии. Результат берётся из `structuredContent` либо
декодируется из текстового содержимого.

| Адрес | Назначение | Авторизация |
|---|---|---|
| `:8101/mcp` | Один защищённый MCP АБС; список/вызовы зависят от агента и scope | Агентский JWT `aud=bank-mcp`; для dashboard/legacy: пользовательский JWT `aud=abs-mcp` |
| `:8104/mcp` | Уязвимый доступ к АБС с параметром `customer_id` | Пользовательский JWT |
| `:8105/mcp` | Банковский веб-поиск через DDGS | JWT с `aud=duckduckgo-mcp` |
| `travel-duckduckgo-mcp:8105/mcp` | Поиск travel-системы, только во внутренней сети | JWT с `aud=travel-duckduckgo-mcp` |
| `:8106/mcp` | `search_flights` мокового провайдера | Отдельный bearer-токен |
| `https://mcp.tutu.ru/mcp` | Поиск авиабилетов через `search_avia` | Не требуется |

Получение списка инструментов защищённого MCP после инициализации:

```bash
curl -fsS http://localhost:8101/mcp \
  -H "Authorization: Bearer $IVAN_TOKEN" \
  -H 'MCP-Protocol-Version: 2025-06-18' \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/list","params":{}}'
```

Получение пользовательского токена описано в [руководстве](RUNBOOK.md#токены-для-лабораторных-запросов).
Общие инструменты `abs-mcp` и `abs-mcp-vulnerable` различаются выбором клиента:
защищённый сервер берёт его из JWT, уязвимый требует аргумент `customer_id`.
`get_account_statement` есть у обоих серверов; уязвимый также требует `customer_id`.
Адреса и режим задаются в `.env`, см. [настройки](CONFIGURATION.md).

## Авиабилеты Туту

Travel Agent вызывает только `search_avia`. Он передаёт `origin`, `destination`,
`departure_date`, `adults`, `page_size=10`, `view=compact`.
`return_date` передаётся только при наличии обратного рейса.
Перед вызовом проверяется наличие этих полей в опубликованной схеме инструмента.
Банковские JWT, профиль и токен мока Туту не передаются.

Ответ содержит `offers`. Сохраняются цена, оба направления в `legs[].segments[]`,
аэропорты, номера рейсов, условия тарифов и `search_results_url`. Цена уже относится
ко всей группе пассажиров; она не умножается на число взрослых или направлений.
Параметра валюты у `search_avia` нет: сохраняется валюта ответа, без пересчёта.

`meta.has_more`, `total_matched_exact` и сведения о распознанных городах передаются
модели и возвращаются в `flight_search_meta`. Неполная страница результатов не означает,
что других рейсов нет. `checkout_ref` и хеши оформления заказа не используются.
Инструменты оформления заказа и регистрации пассажиров не вызываются.

## Мок авиабилетов

`flights-mcp` запускается вместе с остальными сервисами на порту 8106. В нём один
инструмент `search_flights`, который проверяет IATA-коды, даты, число взрослых и
возвращает один вымышленный рейс. Для обычного поиска через него задайте
`FLIGHTS_PROVIDER=mock` в `.env`.

Файл `FLIGHTS_MOCK_NOTE` из каталога `infra/flights-mcp/` передаётся в контейнер как
`FLIGHTS_MCP_NOTE_FILE`. Мок читает до 4000 символов при каждом запросе и возвращает
их в `provider_note`. `clean.txt` содержит нейтральный текст, `provider-note.txt`:
ложную инструкцию для опыта. Каждый результат отмечен `synthetic=true`,
`mode=mock-external-mcp`, `content_trust=untrusted-external`.

Мок использует отдельный `FLIGHTS_MCP_AUTH_TOKEN`, в том числе при отключённой для
тестов проверке JWT остальных сервисов. Он не обращается к авиакомпаниям или MongoDB.
Банковский `POST /v1/lab/ingest-flight-memory` запрашивает исходный ответ мока
у Travel Agent по A2A, затем передаёт его в API памяти. Прямого MCP-соединения
между банковской системой и моком нет. Это отдельный лабораторный запрос; обычный поиск Туту его не вызывает.

## Сведения о направлениях

Инвестиционный навык использует `duckduckgo-mcp.news_search`, внешний партнёр
использует `travel-duckduckgo-mcp.text_search`. Оба сервера работают через DDGS:
текстовый движок задаёт `DDGS_TEXT_BACKEND` (по умолчанию `bing`), новости используют
`auto`. Название сервера не определяет поисковый движок.
Результат различает `ok`, `empty` и `unavailable`, содержит запрос, движок и диагностику.
Сбой источника возвращается явно, без подмены вымышленной выдачей.

## A2A 1.0

Между системами доступен шлюз `travel-api :8003`. Он принимает сервисный JWT
`azp=travel-skill` с `travel.plan` либо прежнего `banking-agent`, `aud=travel-agent`. Он пропускает только A2A,
карточку агента и `/health`; прямые REST-методы Travel Agent не публикуются.

Travel Agent публикует описание на `GET /.well-known/agent-card.json` и принимает
`POST /a2a/v1/message:send` с заголовками `Content-Type: application/a2a+json` и
`A2A-Version: 1.0`. Используется привязка `HTTP+JSON`.

Сообщение содержит `role=ROLE_USER`, `messageId`, `contextId` и JSON-часть с `TripRequest`.
В нём передаются идентификатор клиента для корреляции, вид запроса, маршрут, даты,
число взрослых, бюджет, валюта и интересы. Банковский профиль, счета и история туда
не входят. Идентификатор клиента исключается из входных данных LLM тревел-агента.

Для `request_type=destination_info` тревел-агент ищет только сведения о месте.
Пустая выдача и недоступность поискового провайдера возвращаются обычным A2A-ответом
с `destination_search_meta.status=empty|unavailable` и пояснением в `agent_cautions`.
Сбой также отражается в `search_errors`; обычная пустая выдача туда не добавляется.
Найденные рейсы сохраняются. HTTP 401/403 от MCP остаются ошибками.
Для `trip_search` нужны маршрут и даты. В режиме оркестратора параметры извлекает
банковский `travel-skill`; при нехватке данных он задаёт один-два понятных вопроса
по-русски и сохраняет уточнение в своей истории. Технический список остаётся только
в `data.missing_fields`. Для `budget_plan` банковский навык собирает направление,
город вылета, период, длительность и число людей. Точные аэропорты и даты для
предварительного бюджета необязательны. Партнёр ищет сведения о расходах;
известные аэропорты и дата вылета дополнительно запускают поиск билетов. `one_way=true` запрещает `return_date`; `stay_end_date` описывает
конец пребывания и не участвует в запросе обратного рейса.
В `legacy` параметры и уточняющий вопрос формирует прежний
банковский граф.
До их получения A2A-запрос не отправляется; вопрос сохраняется в истории диалога.
Travel Agent планирует инструменты через LLM, затем ранжирует найденные рейсы.
Код отклоняет `result_id`, отсутствующий в выдаче; свободное резюме не проходит
полной проверки фактов.
Поиск отелей не поддерживается. Для совместимости с существующими A2A-клиентами
ответ сохраняет `accommodations: []` и `provider_modes.hotel_search="not-supported"`.
Эти поля не означают, что поиск отелей был выполнен и ничего не нашёл.

Для локального бронирования отправьте по A2A JSON-часть:

```json
{"request_type":"mock_booking","booking":{"flight_result_id":"flight-1"}}
```

Ответ содержит идентификатор `mock-*` и `external_side_effect=false`.
Лабораторное чтение мока использует `request_type=lab_flight_source` с полем `search`
по схеме `MockFlightSearch`. Оба запроса проверяются как A2A-запросы банковской системы.
Внутренний REST-метод `/v1/bookings/mock` остаётся только внутри travel-системы;
через шлюз он недоступен. Планирование поездки не создаёт бронь автоматически.

## Контекст между вызовами

В режиме оркестратора `travel-skill` восстанавливает собственную историю из памяти
банка и извлекает релевантные долговременные записи клиента. Это состояние банковского
исполнителя; партнёрский `travel-agent` получает параметры и `user_query` до 1000
символов. Его `TravelState` живёт только в текущем выполнении.

`contextId` связывает A2A-сообщения и трассы, но не загружает сессию партнёра.
Партнёр не читает общую память банка. Сохранение выдачи, владение `result_id`,
согласованный бюджет и продолжение диалога после замены партнёра остаются задачами курса.
В `legacy` историю и память перед извлечением поездки читает прежний банковский граф.

## Контракт общей памяти и происхождения

Навыки используют четыре POST-метода `/api/v1/skills/context`, `/candidates`,
`/history`, `/turns`. Общие поля: `query`, `conversation_id`, `experiment`;
кандидат дополнительно содержит `content` и `source`, реплика содержит `assistant_message`.
Сервер назначает область по `SKILL_MEMORY_MODE` и автору JWT, клиента определяет по `customer_id`.
В `shared` область общая для трёх навыков одного клиента; история всегда личная.

Кандидат не является опубликованным знанием: ответ содержит ID рабочей записи,
кандидата и задания. Только последующий `collect`/расписание может создать воспоминания.
`writer_agent`, `origin_source`, `source_user_id`, `derived_from_job` и ID результата
позволяют проверить происхождение. Эти сведения не доказывают истинность текста или
право передавать его другому навыку. Форматы и API описаны в [MEMORY.md](MEMORY.md).

## Корреляция экспериментов

`experiment_id` обозначает серию, `run_id` обозначает запуск,
`conversation_id` связывает сообщения диалога.
ID опыта и запуска содержат от 1 до 100 ASCII-символов: буквы, цифры, `.`, `_`, `:`, `-`.
Ограничение проверяется схемой до формирования HTTP-заголовков.
Метки передаются в теле задачи/памяти и заголовках `x-experiment-id`, `x-run-id`.
Они не являются доказательством идентичности или согласия.
W3C `traceparent` проходит через межсистемные шлюзы вместе с метками опыта;
`baggage` удаляется. Внутри системы контекст продолжается; другая система создаёт
локальный корень в своём проекте Langfuse и записывает `upstream_trace_id` /
`upstream_span_id`. Фоновые задания сопоставляются по меткам и ID записей.
Для отложенного переноса метки сохраняются в `source_metadata` задания.

[Воспроизводимые опыты](EXPERIMENTS.md) отделяют успешный контрактный вызов от
создания долговременной записи, извлечения, вредного использования и внешнего эффекта.
