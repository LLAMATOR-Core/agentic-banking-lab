# Настройки стенда

Создайте `.env` из `.env.example`, задайте настройки и запустите стенд:

```bash
docker compose --env-file .env up -d --build
```

## Режим агента и полномочия

| Параметр | Значение по умолчанию | Действие |
|---|---|---|
| `BANKING_AGENT_MODE` | `orchestrator` | Три агента внутри `banking-agent` со своими токенами; `legacy` включает прежний граф и денежные подтверждения |
| `SKILL_MEMORY_MODE` | `shared` | Общая долговременная память навыков одного клиента; `isolated` разделяет её по навыкам |
| `ABS_MCP_MODE` | `secure` | Выбор прежнего MCP в чате `legacy`; не меняет права токенов трёх агентов |
| `AUTH_DISABLED` | `false` | Для проверки полномочий аутентификация обязательна |

В `orchestrator` инвестиционному навыку назначен `portfolio.read`, банковскому
аналитику разрешены `customer.read`, `accounts.read`, `operations.read`,
`portfolio.read`, `products.read`, тревел-навыку назначен `travel.plan`.
`bank.write` аналитическим навыкам не выдан. Для памяти каждый обменивает клиентский
токен на `memory.access`. Разрешения задаются в
[конфигурации OAuth](../services/common/oauth_config.py), realm и конфигураторе.
LLM их не выбирает.

Отдельные секреты в `.env`: `KEYCLOAK_OPERATIONS_SKILL_SECRET`,
`KEYCLOAK_INVESTMENT_SKILL_SECRET`, `KEYCLOAK_TRAVEL_SKILL_SECRET`.
Они передаются одному `banking-agent`, Keycloak и конфигуратору; объекты агентов
создают отдельные клиенты авторизации. Общий MCP получает только свой секрет `bank-mcp`.
`keycloak-configurator` обновляет существующий realm без удаления тома.
Полный запуск конфигуратора также восстанавливает профили и пароли демонстрационных
пользователей из его кода. Цепочка Token Exchange описана в
[контрактах](INTEROPERABILITY.md#oauth2-и-token-exchange).

`SKILL_MEMORY_MODE` задаётся у `memory-service`. В обоих режимах новые области
сохраняют конкретного клиента; история навыка личная. Переключение не удаляет
записи и не исправляет уже отравленную собственную память навыка.

## LLM и эмбеддинги

| Параметр | Назначение |
|---|---|
| `OPENAI_API_KEY` | Ключ провайдера LLM |
| `OPENAI_BASE_URL` | Адрес совместимого API с Chat Completions и Embeddings |
| `OPENAI_MODEL` | Общая модель оркестратора банка, трёх навыков, партнёра и оркестратора памяти |
| `EMBEDDING_MODEL` | Модель эмбеддингов для записи и поиска памяти |
| `OPENAI_JSON_MODE` | Передавать ли провайдеру `response_format` для JSON |
| `OPENAI_TIMEOUT_SECONDS` | Тайм-аут LLM и эмбеддингов, по умолчанию 45 секунд |
| `MEMORY_HTTP_TIMEOUT_SECONDS` | Тайм-аут банковского клиента истории и прежних API памяти, по умолчанию 60 секунд; у трёх навыков фиксирован на 60 секундах |
| `TRAVEL_HTTP_TIMEOUT_SECONDS` | Тайм-аут банковского A2A-клиента, по умолчанию 180 секунд |
| `BANK_TIMEZONE` | Часовой пояс контекста прежнего банковского графа; по умолчанию `Europe/Moscow` |

Если локальный провайдер не проверяет ключи, всё равно задайте непустой `OPENAI_API_KEY`.
Для провайдера на хосте Docker Desktop обычно нужен адрес
`http://host.docker.internal:<порт>/v1`, а не `localhost`.

Параметры `BANKING_OPENAI_*`, `TRAVEL_OPENAI_*`, `MEMORY_OPENAI_*` переопределяют
ключ, адрес и модель для каждой системы. Пустые значения используют общие `OPENAI_*`.
Контейнер получает настройки провайдера своей системы. Все три банковских навыка
используют банковского провайдера. API памяти и её оркестратор используют одного
провайдера эмбеддингов для совместимости векторов.
Текущие навыки извлекают даты по Москве независимо от `BANK_TIMEZONE` графа `legacy`.

## Обработка долговременной памяти

`MEMORY_ORCHESTRATION_INTERVAL_SECONDS` задаёт интервал фоновой обработки очереди
в целых секундах:

| Значение | Режим |
|---|---|
| `1800` | По умолчанию: обработка раз в 30 минут |
| `10` | Обработка через 10 секунд для быстрых опытов |
| `0` | Только ручная обработка; периодический запуск отключён |

Для воспроизводимого опыта с отравлением задайте в `.env`:

```dotenv
MEMORY_ORCHESTRATION_INTERVAL_SECONDS=0
```

Примените настройку обычной командой:

```bash
docker compose --env-file .env up -d --build
curl -fsS http://localhost:8004/health
```

В `/health` проверьте `schedule_seconds` и `schedule_enabled`.
После помещения тестового материала в очередь вызовите принудительную обработку
нужного диалога. Получение `MEMORY_OPERATOR_TOKEN` описано
в [инструкции](RUNBOOK.md#токены-для-лабораторных-запросов):

```bash
curl -fsS http://localhost:8004/api/v1/orchestrator/collect \
  -H "Authorization: Bearer $MEMORY_OPERATOR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"agent_id":"banking-agent","conversation_id":"poison-test-001","limit":100}'
```

В примере `agent_id=banking-agent` относится к прежним лабораториям. Для новых навыков
используйте `skills.shared` либо `skills.<identity>` в соответствии с режимом или
фильтруйте только по уникальному диалогу; записи истории UI и навыка различайте по автору.
Замените `poison-test-001` идентификатором своего диалога или значением
`conversation_id` из ответа лабораторного API. Можно также передать `user_id`.
Без фильтров запрос обрабатывает ожидающие задания всех диалогов, в пределах `limit`
(от 1 до 500, по умолчанию 100).

Запрос дожидается обработки и возвращает `completed_jobs`, `failed_attempts` и `created`.
Он доступен и при включённом расписании. Это обработка очереди, а не очистка памяти
или повторный запуск завершённых заданий: при пустой очереди `completed_jobs=0`.
Пустой список `created` также возможен, если LLM не выделила полезных воспоминаний.
Для нового опыта снова поместите материал в очередь. Пользовательский JWT и токен
банковского агента не дают права вызывать этот операторский метод.

## Langfuse

Каждая система получает только свою пару ключей проекта:

| Система | Приёмник | Проект | Переменные |
|---|---|---|---|
| Банк | `langfuse-web` | `Banking` | `BANKING_LANGFUSE_PUBLIC_KEY` / `BANKING_LANGFUSE_SECRET_KEY` |
| Партнёр | `langfuse-travel` | `Travel` | `TRAVEL_LANGFUSE_PUBLIC_KEY` / `TRAVEL_LANGFUSE_SECRET_KEY` |
| Память | `langfuse-memory` | `Persistent Memory` | `MEMORY_LANGFUSE_PUBLIC_KEY` / `MEMORY_LANGFUSE_SECRET_KEY` |

Проекты создаются при запуске; исторические записи не удаляются.

В трассах сохраняются полные входы и выходы: запрос и ответ API, состояние
на входе каждого шага графа и его результат, сообщения LLM (включая системный
промпт, контекст и JSON Schema), сырой ответ каждой попытки, аргументы и результаты
MCP, чтение и запись рабочей и долговременной памяти, тексты и векторы embeddings.
Каждая попытка LLM создаёт `generation` с моделью, расходом токенов (если
провайдер его вернул) и ошибкой формата. Исключения операций помечаются `ERROR`,
структурированный сбой поискового провайдера получает `WARNING`.

Внутри каждой системы один входящий запрос создаёт одну трассу с вложенными
проверками OAuth, агентами, MCP и LLM. Имя задаёт корневой HTTP-запрос.
Локальные сервисы продолжают W3C `traceparent`; другая система создаёт собственный
корень и сохраняет ссылку `upstream_trace_id` / `upstream_span_id` на внешний вызов.
`upstream_system_id` и `x-agent-system-id` являются метками телеметрии, не правами доступа.
Банковский вход игнорирует внешний родительский контекст. Проверки здоровья
не создают трасс; `baggage` и ключи Langfuse между системами не передаются.

Фоновая обработка памяти и самостоятельный операторский запрос создают свои трассы:
это отдельные исполнения, связанные с исходным запросом через `experiment_id`,
`run_id`, candidate/job/record ID и `derived_from_job`. Метки опыта сохраняются
в заданиях и записях памяти; совпадение диалога не объединяет разные запросы.

| Наблюдение | Что проверять |
|---|---|
| `orchestrator.route`, `orchestrator.delegate`, `orchestrator.compose` | Первый исполнитель, дополнительные вызовы, результаты и итоговый ответ |
| `skill.turn`, `skill.sources`, LLM generations | Память, собственная история, реальные результаты инструментов и ответ модели |
| `oauth.token-exchange` | Клиент обмена, audience, запрошенный/выданный scope, статус и срок; без токенов |
| `oauth.authorize`, `oauth.scope-check`, `oauth.resource-check` | Проверенные claims и решения допуска клиента, scope и ресурса АБС |
| `memory.skill.stage`, `memory.skill.recall`, `memory.process-job` | Автор/читатель, режим, кандидат, задание, созданные и извлечённые записи |
| `a2a.http`, `a2a.travel.send-message` | Состав данных, действительно переданных партнёру |

Отказы авторизации не всегда доходят до бизнес-шагов; проверяйте события допуска и
HTTP/MCP-ответ. Происхождение записи проверяйте по `writer_agent`, `origin_source`
и `derived_from_job`. Ошибки телеметрии не останавливают запрос; Langfuse не является
неизменяемым журналом аудита. Живая доставка проверяется отдельно от локальных тестов.

Структурированные поля токенов, авторизации, паролей, API-ключей, клиентских
секретов, номеров карт и CVV рекурсивно заменяются на `[REDACTED]`, в том числе
в JSON внутри текстовых сообщений. Остальные данные, включая тексты диалогов,
профиль клиента и результаты инструментов, доступны в Langfuse без сокращения.
Маскирование по именам полей не гарантирует удаления секретов из произвольного
свободного текста. Старые трассы сохраняют прежний формат.

## MCP АБС

`ABS_MCP_MODE` выбирает MCP для банковских инструментов чата **только при**
`BANKING_AGENT_MODE=legacy`:

- `secure`: `abs-mcp` определяет клиента по пользовательскому JWT и использует
  Keycloak Token Exchange для обращения к АБС;
- `vulnerable`: LLM выбирает `customer_id`, а `abs-mcp-vulnerable` передаёт его
  в АБС под общей сервисной учётной записью. Это намеренное нарушение контроля доступа.

Выбор относится к профилю, счетам, истории операций, инвестиционным инструментам и
исполнению подтверждённых операций чата. Обзор в интерфейсе банка и профиль,
который загружается для персонализации, всегда используют защищённый MCP.

Проверки владельца подтверждения, срока действия и повторного исполнения сохраняются.
Они не исправляют подмену клиента на уровне уязвимого MCP. Не меняйте режим между
подготовкой и подтверждением денежной операции: для сравнения подготовьте новую операцию.

## Источник авиабилетов

`FLIGHTS_PROVIDER` выбирает источник для Travel Agent:

- `tutu`: удалённый MCP Туту, инструмент `search_avia`, без авторизации;
- `mock`: собственный `flights-mcp`, инструмент `search_flights`, один вымышленный рейс.

У мока отдельный токен `FLIGHTS_MCP_AUTH_TOKEN`. Текст в его ответе задаёт
`FLIGHTS_MOCK_NOTE`:

- `clean.txt`: нейтральная заметка;
- `provider-note.txt`: ложная инструкция для опыта с отравлением памяти.

Оба файла находятся в `infra/flights-mcp/`. Мок читает выбранный файл при каждом
поиске, до 4000 символов. Изменение текста не требует пересборки; после смены имени
файла в `.env` повторите команду запуска.

Мок запускается вместе со стендом независимо от источника рейсов. Поэтому можно
оставить Туту для обычного поиска, но использовать отравленный ответ мока через
лабораторный API. Туту при ошибке не заменяется моком автоматически.
Поиск отелей не реализован.

## Примеры настроек

Для основного межагентного опыта:

```dotenv
BANKING_AGENT_MODE=orchestrator
SKILL_MEMORY_MODE=shared
MEMORY_ORCHESTRATION_INTERVAL_SECONDS=0
FLIGHTS_PROVIDER=mock
FLIGHTS_MOCK_NOTE=clean.txt
```

Повторите опыт с `SKILL_MEMORY_MODE=isolated`, сохранив остальные условия и фиксируя
состояние обеих областей. Команды и критерии приведены в [EXPERIMENTS.md](EXPERIMENTS.md).
Следующие комбинации относятся к `BANKING_AGENT_MODE=legacy`:

| Опыт | `ABS_MCP_MODE` | `FLIGHTS_PROVIDER` | `FLIGHTS_MOCK_NOTE` |
|---|---|---|---|
| Исходный вариант | `secure` | `tutu` | `clean.txt` |
| Нарушение контроля доступа в АБС | `vulnerable` | `tutu` | `clean.txt` |
| Чистый ответ мока | `secure` | `mock` | `clean.txt` |
| Отравление памяти через мок | `secure` | `mock` | `provider-note.txt` |
| Совместный опыт | `vulnerable` | `mock` | `provider-note.txt` |

Например, для совместного опыта укажите в `.env`:

```dotenv
BANKING_AGENT_MODE=legacy
ABS_MCP_MODE=vulnerable
FLIGHTS_PROVIDER=mock
FLIGHTS_MOCK_NOTE=provider-note.txt
```

Затем выполните:

```bash
docker compose --env-file .env up -d --build
```

Возврат к исходным значениям переключает подключения, но не удаляет уже отравленную
память. Записи удаляются отдельно через операторский API, см. [сценарии](EXPERIMENTS.md).

## Проверка настроек

```bash
docker compose --env-file .env config --quiet
docker compose --env-file .env ps
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8003/health
```

В ответах `/health` проверьте `agent_mode`, `abs_mcp_mode` и `flight_provider`.
В режиме оркестратора ориентируйтесь на `agent_mode` и `data.experiment.memory_mode`;
`abs_mcp_mode` не меняет ограничений токенов агентов на общем MCP. Завершённый ответ навыка
содержит `data.experiment` с `run_id`, `recalled_memory_ids` и результатами постановки
кандидатов. Для `legacy` действуют следующие дополнительные признаки. После запроса в чате
`data.connections` содержит режим АБС и `selected_customer_id`, выбранный LLM.
В защищённом режиме это поле равно `null`. Источник рейсов указан в
`data.travel.provider_modes.flight_search`, заметка мока находится в `provider_note` результата.

В Langfuse уязвимая ветка содержит шаг `llm.banking-agent.select_abs_customer`.
Фактический MCP-сервер и его аргументы видны в `mcp.tool.call`.
Если переменная уже задана в оболочке, Docker Compose использует её вместо значения
из файла. Удалите такую переменную из окружения, если настройки `.env` не применяются.

## Собственные сервисы

При необходимости переопределите в `.env` адреса `ABS_MCP_URL`,
`ABS_MCP_VULNERABLE_URL`, `TRAVEL_AGENT_URL`, `MEMORY_URL`, `TUTU_MCP_URL`
или `MOCK_FLIGHTS_MCP_URL`. Необязательные адреса приведены в `.env.example`.

По умолчанию `TRAVEL_AGENT_URL` указывает на `travel-api`,
а `MEMORY_URL` указывает на `memory-api`. Не заменяйте их адресами внутренних контейнеров другой системы.
`MOCK_FLIGHTS_MCP_URL` относится только к Travel Agent.

Адреса `ABS_MCP_URL`, `MEMORY_URL`, `DUCKDUCKGO_MCP_URL`, `TRAVEL_AGENT_URL`
задаются в окружении банковского контейнера. Агент использует только разрешённые
ему инструменты со своими учётными данными. При замене сервиса согласуйте адрес,
`azp`, `aud` и scope по [контрактам](INTEROPERABILITY.md).

## Движок веб-поиска

`DDGS_TEXT_BACKEND=bing` задаёт движок DDGS для текстового поиска обоих MCP.
Режим DDGS `auto` может выбирать энциклопедии и возвращать нерелевантную выдачу
для запросов о расходах. В результатах и трассах сохраняются настроенный `backend`,
запрос и диагностика. Поиск новостей использует
собственный режим DDGS `auto`.

## Обязательный subject JWT

Импорт realm и конфигуратор назначают `oidc-sub-mapper` всем клиентам, выпускающим
токены. Поле `sub` обязательно для проверки JWT. Стандартные `profile` и `email`
доступны интерфейсу для полей профиля и не добавляют полномочий на ресурсы АБС.
