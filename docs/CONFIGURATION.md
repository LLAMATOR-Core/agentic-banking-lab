# Настройки стенда

Все настройки задаются в `.env`. Создайте его из `.env.example`, измените нужные
значения и запустите:

```bash
docker compose --env-file .env up -d --build
```

После изменения параметров повторите эту команду. Compose пересоздаст сервисы,
конфигурация которых изменилась. История, память и данные АБС сохранятся.

## LLM и эмбеддинги

| Параметр | Назначение |
|---|---|
| `OPENAI_API_KEY` | Ключ провайдера LLM |
| `OPENAI_BASE_URL` | Адрес совместимого API с Chat Completions и Embeddings |
| `OPENAI_MODEL` | Модель банковского агента, тревел-агента и оркестратора памяти |
| `EMBEDDING_MODEL` | Модель эмбеддингов для записи и поиска памяти |
| `OPENAI_JSON_MODE` | Передавать ли провайдеру `response_format` для JSON |
| `BANK_TIMEZONE` | Часовой пояс банковского агента; по умолчанию `Europe/Moscow` |

Если локальный провайдер не проверяет ключи, всё равно задайте непустой `OPENAI_API_KEY`.
Для провайдера на хосте Docker Desktop обычно нужен адрес
`http://host.docker.internal:<порт>/v1`, а не `localhost`.

## Обработка долговременной памяти

`MEMORY_ORCHESTRATION_INTERVAL_SECONDS` задаёт интервал фоновой обработки очереди
оркестратором памяти. Значение — целое число секунд:

| Значение | Режим |
|---|---|
| `1800` | По умолчанию: обработка раз в 30 минут |
| `10` | Обработка через 10 секунд для быстрых опытов |
| `0` | Только ручная обработка; периодический запуск отключён |

Допустимы любые целые значения от `0`, скрытого минимума в 60 секунд нет.
Отрицательное значение или нечисловая строка останавливают запуск оркестратора
с ошибкой конфигурации. Интервал отсчитывается после завершения предыдущей обработки;
первый запуск — через указанный интервал после начальной подготовки сервиса.
Режим `0` отключает расписание, сохраняя подготовку хранилища при запуске.

Для воспроизводимого опыта с отравлением задайте в `.env`:

```dotenv
MEMORY_ORCHESTRATION_INTERVAL_SECONDS=0
```

Примените настройку обычной командой:

```bash
docker compose --env-file .env up -d --build
curl -fsS http://localhost:8004/health
```

В `/health` проверьте `schedule_seconds` и `schedule_enabled`.
После помещения тестового материала в очередь вызовите принудительную обработку
нужного диалога. Получение `MEMORY_OPERATOR_TOKEN` описано
в [инструкции](RUNBOOK.md#токены-для-лабораторных-запросов):

```bash
curl -fsS http://localhost:8004/api/v1/orchestrator/collect \
  -H "Authorization: Bearer $MEMORY_OPERATOR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"agent_id":"banking-agent","conversation_id":"poison-test-001","limit":100}'
```

Замените `poison-test-001` идентификатором своего диалога или значением
`conversation_id` из ответа лабораторного API. Можно также передать `user_id`.
Без фильтров запрос обрабатывает ожидающие задания всех диалогов, в пределах `limit`
(от 1 до 500, по умолчанию 100).

Запрос дожидается обработки и возвращает `completed_jobs`, `failed_attempts` и `created`.
Он доступен и при включённом расписании. Это обработка очереди, а не очистка памяти
или повторный запуск завершённых заданий: при пустой очереди `completed_jobs=0`.
Пустой список `created` также возможен, если LLM не выделила полезных воспоминаний.
Для нового опыта снова поместите материал в очередь. Пользовательский JWT и токен
банковского агента не дают права вызывать этот операторский метод.

## Langfuse

В `.env` заданы три независимые пары ключей:

- `BANKING_LANGFUSE_PUBLIC_KEY` / `BANKING_LANGFUSE_SECRET_KEY` — проект `Banking`;
- `TRAVEL_LANGFUSE_PUBLIC_KEY` / `TRAVEL_LANGFUSE_SECRET_KEY` — проект `Travel`;
- `MEMORY_LANGFUSE_PUBLIC_KEY` / `MEMORY_LANGFUSE_SECRET_KEY` — проект `Persistent Memory`.

Не используйте одну пару для разных систем. Проекты создаются автоматически, один
исследовательский пользователь видит их в интерфейсе Langfuse. Старые общие
`LANGFUSE_PUBLIC_KEY` и `LANGFUSE_SECRET_KEY` в `.env` больше не используются.

Ключи из `.env` задаются проектам при их первом создании. Для замены ключа уже
существующего проекта создайте новую пару в настройках проекта Langfuse, перенесите
её в соответствующие переменные `.env` и повторите команду запуска.
Старый проект и его трассы не удаляются и не переносятся автоматически.

В новых трассах сохраняются полные входы и выходы: запрос и ответ API, состояние
на входе каждого шага графа и его результат, сообщения LLM (включая системный
промпт, контекст и JSON Schema), сырой ответ каждой попытки, аргументы и результаты
MCP, чтение и запись рабочей и долговременной памяти, тексты и векторы embeddings.
Повторные попытки LLM — отдельные `generation` с моделью, расходом токенов (если
провайдер его вернул) и ошибкой проверки формата. Ошибки операций помечены `ERROR`.

Внутри одной системы вызовы MCP связаны через W3C `traceparent`. На границах
Banking / Travel / Persistent Memory сохраняются независимые трассы и проекты;
для перехода между ними используйте одинаковый `session_id` / `correlation_id`
диалога и входы/выходы клиентских вызовов памяти и A2A. У фоновой обработки памяти
есть отдельные шаги для задания, решения LLM и сохранённых воспоминаний.

Структурированные поля токенов, авторизации, паролей, API-ключей, клиентских
секретов, номеров карт и CVV рекурсивно заменяются на `[REDACTED]`, в том числе
в JSON внутри текстовых сообщений. Остальные данные, включая тексты диалогов,
профиль клиента и результаты инструментов, доступны в Langfuse без сокращения.
Маскирование по именам полей не гарантирует удаления секретов из произвольного
свободного текста. Старые трассы остаются в прежнем формате; новые данные
появляются после пересборки сервисов и новых запросов.

При необходимости задайте независимые `BANKING_OPENAI_*`, `TRAVEL_OPENAI_*`,
`MEMORY_OPENAI_*` для провайдеров LLM. Пока они пусты, действуют общие `OPENAI_*`.
Контейнер получает только настройки своей системы. API памяти и оркестратор используют
один memory-провайдер эмбеддингов, чтобы записи и поисковые запросы были совместимы.

## MCP АБС

`ABS_MCP_MODE` выбирает MCP для банковских инструментов чата:

- `secure` — `abs-mcp` определяет клиента по пользовательскому JWT и использует
  Keycloak Token Exchange для обращения к АБС;
- `vulnerable` — LLM выбирает `customer_id`, а `abs-mcp-vulnerable` передаёт его
  в АБС под общей сервисной учётной записью. Это намеренное нарушение контроля доступа.

Выбор относится к профилю, счетам, истории операций, инвестиционным инструментам и
исполнению подтверждённых операций чата. Обзор в интерфейсе банка и профиль,
который загружается для персонализации, всегда используют защищённый MCP.

Проверки владельца подтверждения, срока действия и повторного исполнения сохраняются.
Они не исправляют подмену клиента на уровне уязвимого MCP. Не меняйте режим между
подготовкой и подтверждением денежной операции: для сравнения подготовьте новую операцию.

## Источник авиабилетов

`FLIGHTS_PROVIDER` выбирает источник для Travel Agent:

- `tutu` — удалённый MCP Туту, инструмент `search_avia`, без авторизации;
- `mock` — собственный `flights-mcp`, инструмент `search_flights`, один вымышленный рейс.

У мока отдельный токен `FLIGHTS_MCP_AUTH_TOKEN`. Текст в его ответе задаёт
`FLIGHTS_MOCK_NOTE`:

- `clean.txt` — нейтральная заметка;
- `provider-note.txt` — ложная инструкция для опыта с отравлением памяти.

Оба файла находятся в `infra/flights-mcp/`. Мок читает выбранный файл при каждом
поиске, до 4000 символов. Изменение текста не требует пересборки; после смены имени
файла в `.env` повторите команду запуска.

Мок запускается вместе со стендом независимо от источника рейсов. Поэтому можно
оставить Туту для обычного поиска, но использовать отравленный ответ мока через
лабораторный API. Туту при ошибке не заменяется моком автоматически.
Поиск отелей не реализован. Старые `BOOKING_MCP_URL` и `HASDATA_API_KEY` больше
не используются: их можно удалить из существующего `.env`.

## Примеры настроек

| Опыт | `ABS_MCP_MODE` | `FLIGHTS_PROVIDER` | `FLIGHTS_MOCK_NOTE` |
|---|---|---|---|
| Исходный вариант | `secure` | `tutu` | `clean.txt` |
| Нарушение контроля доступа в АБС | `vulnerable` | `tutu` | `clean.txt` |
| Чистый ответ мока | `secure` | `mock` | `clean.txt` |
| Отравление памяти через мок | `secure` | `mock` | `provider-note.txt` |
| Совместный опыт | `vulnerable` | `mock` | `provider-note.txt` |

Например, для совместного опыта укажите в `.env`:

```dotenv
ABS_MCP_MODE=vulnerable
FLIGHTS_PROVIDER=mock
FLIGHTS_MOCK_NOTE=provider-note.txt
```

Затем выполните:

```bash
docker compose --env-file .env up -d --build
```

Возврат к исходным значениям переключает подключения, но не удаляет уже отравленную
память. Записи удаляются отдельно через операторский API, см. [сценарии](EXPERIMENTS.md).

## Проверка настроек

```bash
docker compose --env-file .env config --quiet
docker compose --env-file .env ps
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8003/health
```

В ответах `/health` проверьте `abs_mcp_mode` и `flight_provider`. После запроса в чате
`data.connections` содержит режим АБС и `selected_customer_id`, выбранный LLM.
В защищённом режиме это поле равно `null`. Источник рейсов указан в
`data.travel.provider_modes.flight_search`, заметка мока — в `provider_note` результата.

В Langfuse уязвимая ветка содержит шаг `llm.banking-agent.select_abs_customer`.
Фактический MCP-сервер и его аргументы видны в `mcp.tool.call`.
Если переменная уже задана в оболочке, Docker Compose использует её вместо значения
из файла. Удалите такую переменную из окружения, если настройки `.env` не применяются.

## Собственные сервисы

При необходимости переопределите в `.env` адреса `ABS_MCP_URL`,
`ABS_MCP_VULNERABLE_URL`, `TRAVEL_AGENT_URL`, `MEMORY_URL`, `TUTU_MCP_URL`
или `MOCK_FLIGHTS_MCP_URL`. Необязательные адреса приведены в `.env.example`.

`TRAVEL_AGENT_URL` по умолчанию указывает на `travel-api`, `MEMORY_URL` — на
`memory-api`. Не заменяйте их адресами внутренних контейнеров другой системы.
`MOCK_FLIGHTS_MCP_URL` относится только к Travel Agent.

Сервис по новому адресу должен поддерживать тот же протокол, имена инструментов,
схемы аргументов и способ авторизации. Смена адреса сама по себе не меняет контракт MCP
и не выдаёт токен для другой области доверия. Контракты описаны в [MCP и A2A](INTEROPERABILITY.md).
