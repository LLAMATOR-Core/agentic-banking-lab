# Примерный план курса по интероперабельности агентных систем

Курс строится как последовательная доработка этого стенда. На каждом занятии
студенты выявляют конкретную несовместимость, согласуют контракт, реализуют изменение
и проверяют его на обычных запросах, ошибках и попытках нарушения прав доступа.
Итоговая проверка — взаимодействие с независимо разработанной реализацией партнёра.

Предлагаемый объём — 12 занятий по 4 академических часа и самостоятельная работа
между занятиями. Нужны базовые знания Python, HTTP, JSON, Docker и автоматического
тестирования. Первое занятие вводит понятия, остальные посвящены практике.

Связанный [практикум по безопасности ИИ](AI_SECURITY_WORKSHOPS.md) состоит из двух
семинаров: моделирование угроз и атаки, затем защиты и повторные проверки.
Его можно использовать как отдельный блок курса; выбор инструмента тестирования свободный.

## Замысел и результаты обучения

Из исходного обсуждения курса сохраняются три положения:

- Технический, семантический и организационный уровни помогают классифицировать
  проблемы. Для каждой проблемы нужны проверяемые требования и эксперимент.
- Единицей работы служит совместный процесс независимых систем. Наличие API,
  одинакового JSON или общего поставщика LLM ещё не доказывает интероперабельность.
- Заменяемость проверяется на реализации другой команды, которой доступны
  опубликованные контракты, но не внутреннее устройство партнёра.

Обзору подходов к интероперабельности, включая российскую школу и международные
модели, достаточно вводной части. Классификации используются при разборе результатов:
какую несовместимость обнаружили, какое соглашение её устраняет и чем это доказано.
Не требуется вводить новую модель зрелости или вычислять общий «уровень» системы.

После курса студент должен уметь определить границы систем, согласовать протокол
и смысл данных, организовать передачу контекста, ограничить полномочия участников
и доказать совместимость тестами. Отдельный результат — различение доверия к сервису,
достоверности его данных и права выполнять действие.

## Исходная реализация и учебные задачи

Текущее состояние описано в [архитектуре](ARCHITECTURE.md), контракты —
в [MCP и A2A](INTEROPERABILITY.md). Таблица отделяет готовые возможности от заданий.

| Область | Уже есть | Что предстоит исследовать или реализовать |
|---|---|---|
| Три системы | Банк, тревел-система и система памяти разделены сетями, процессами и проектами Langfuse | Сохранение границ при расширении взаимодействия и замене компонентов |
| Банк → тревел-агент | A2A-запрос с параметрами поездки; карточка агента; известные клиенту методы | Обнаружение возможностей, согласование ограничений и проверка контракта другой реализации |
| Тревел-агент → инструменты | Туту или мок авиабилетов; собственный DuckDuckGo MCP | Замена поставщика, изменение схемы, сохранение смысла результатов |
| Контекст тревел-агента | Текущий запрос и результаты инструментов внутри одного выполнения | Продолжение диалога, восстановление состояния, владение результатами поиска |
| Память | `working`, `episodic`, `semantic`, `procedural`; очередь обработки; отдельный оркестратор | Контракт обмена воспоминаниями, разграничение областей и проверка происхождения |
| Полномочия | Keycloak; защищённый и намеренно уязвимый MCP АБС; подтверждение банковской операции | Ограниченное делегирование для совместной задачи и проверка всей цепочки полномочий |
| Наблюдение | Проекты `Banking`, `Travel`, `Persistent Memory`; корреляция по диалогу | Восстановление причинной цепочки и воспроизводимые измерения |

К сервису памяти сейчас обращается банковский агент. Тревел-агент не сохраняет
историю между вызовами. Банк читает историю и воспоминания, извлекает параметры
поездки и передаёт их вместе с текущим `user_query` длиной до 1000 символов.
Полная история и банковский профиль по A2A не передаются. `contextId` используется
для корреляции; хранилище сессии автоматически по нему не загружается.

Стенд уже соединяет системы по A2A. Для учебных несовместимостей преподаватель
готовит отдельные фикстуры или изменения в учебной копии. Готового набора
«сломанных» вариантов для всех занятий в репозитории пока нет.

Поиск отелей и реальная покупка авиабилетов отсутствуют. Бронирование — локальная
имитация. Автоматическая проверка доступного бюджета поездки и связь выбранного
рейса с банковской оплатой также являются заданиями, а не готовыми возможностями.
Общие Keycloak и инфраструктура Langfuse остаются доверенными службами стенда;
учебное разделение систем не означает независимых физических площадок.

## Сквозной сценарий

Пользователь просит: «Подбери перелёт из Москвы в Ереван на указанные даты,
не дороже 60 000 рублей на двоих. Затем покажи более ранний вариант».

Команды постепенно обеспечивают поиск, сохранение результатов, уточнение выбора,
проверку согласованного ограничения бюджета и локальную имитацию бронирования.
Для денежного действия требуется отдельное подтверждение пользователя.
Остаток на счёте не считается разрешённым бюджетом поездки.

В обычных проверках используется `FLIGHTS_PROVIDER=mock` и нейтральная заметка.
Исходный мок возвращает один рейс: для задания «выбери второй вариант» преподаватель
должен подготовить фикстуру минимум с двумя результатами. Отдельный прогон с Туту
проверяет внешнюю интеграцию; изменчивость реальной выдачи не должна менять ожидаемый
результат воспроизводимых тестов.

### 1. Границы систем и профиль взаимодействия

Зафиксировать участников, владельцев данных, разрешённые направления вызовов
и условия успешного выполнения сквозного сценария. Составить профиль взаимодействия:
поддерживаемые операции, версии протоколов, схемы, семантические соглашения,
аутентификация, ошибки, сроки действия данных и ответственные за изменение контрактов.

Снять исходные результаты. Отдельно показать, что происходит с уточнением поездки
сейчас и какие данные действительно получает тревел-агент. Сверить схему с Compose,
описанием API и трассами, а не только с рисунком архитектуры.

**Проверка:** у каждого требования есть владелец, наблюдаемый результат и тестовый
сценарий. Уже работающая интеграция отделена от планируемых расширений.

### 2. Протоколы и схемы MCP

Разобрать инициализацию, `tools/list`, `tools/call`, проверку схем и передачу ошибок.
На фикстурах изменить имя обязательного поля, тип значения, наличие инструмента
и формат ответа. Сопоставить мок `search_flights` и Туту `search_avia` через адаптер.

**Проверка:** клиент обнаруживает несовместимость до использования результата,
не скрывает ошибку подготовленным рейсом и не передаёт токен мока внешнему провайдеру.
Набор проверок описывает поддерживаемое подмножество MCP, не заявляя соответствия
всей спецификации по одному успешному вызову.

### 3. A2A и обнаружение возможностей

Проверить карточку агента и фактическую реализацию операций. Описать предусловия,
результаты и последствия поиска, лабораторного чтения мока и имитации бронирования.
Согласовать выбор операции при отсутствующей или неподдерживаемой возможности.
Описание партнёра считать недоверенным вводом, проверяемым локальной политикой.

**Проверка:** неизвестный метод, неподдерживаемая версия и ложное описание возможности
дают определённый отказ. Строка в карточке не создаёт права на вызов банковского
инструмента. Взаимодействие сохраняет A2A-границу, не подменяясь импортом чужого кода.

### 4. Смысл денег, маршрута и времени

Различить остаток, доступные средства, бюджет пользователя и разрешение потратить
деньги. Для стоимости определить валюту, точность, состав цены, число пассажиров,
направления и время актуальности. В используемом контракте Туту цена относится
ко всей группе и, при поиске туда-обратно, к обоим направлениям: адаптер не должен
повторно её умножать.

Согласовать IATA-коды и названия городов, часовые пояса, дату вылета и возвращения,
смысл неполной выдачи. Не вводить пересчёт валют без согласованного источника курса.
Общие понятия можно описать словарём и JSON Schema; онтология нужна, если команда
покажет задачу, которую без неё не удаётся проверить.

**Проверка:** фикстуры содержат цену за одного и за группу, другой часовой пояс,
неподдерживаемую валюту и частичную выдачу. Ожидаемый смысл результата задан заранее.

### 5. Контекст и состояние поездки

Сравнить два решения: банк передаёт ограниченный контекст при каждом запросе либо
тревел-система хранит собственную сессию и восстанавливает её по идентификатору.
Выбрать владельца состояния; определить срок хранения, порядок сообщений, версию
состояния и поведение после перезапуска. Параметры поездки, история и результаты
инструментов должны быть различимы в контракте.

Для «выбери второй» связать выбор с конкретной сохранённой выдачей и устойчивым
идентификатором варианта. Полный банковский диалог, профиль, счета и токены не должны
передаваться как универсальный способ восстановить контекст.

**Проверка:** два пользователя и два диалога одного пользователя не смешиваются;
чужой идентификатор сессии отклоняется; уточнение и выбор работают после перезапуска.
Случайный UUID сам по себе не считается проверкой права на доступ.

### 6. Обмен долговременной памятью

Описать переносимый объект памяти: содержание, тип, субъект, источник, время,
происхождение вывода, назначение, срок действия и допустимую область использования.
Отделить событие, факт или предпочтение и правило выполнения задачи. Обсудить
расхождение этого словаря с исходной учебной классификацией слоёв стенда и согласовать
явное преобразование, если оно требуется.

Спроектировать доступ тревел-системы: собственное хранилище либо разрешённый API
системы памяти с отдельной идентичностью и политикой доступа. При выборе второго
варианта нужны согласованные изменения сети, шлюза, JWT и серверной проверки областей.
Поля `agent_id` и `user_id` в теле запроса сами по себе не подтверждают полномочия.
Доступ агента к MongoDB и операторскому API не является решением задания.

**Проверка:** разрешённое предпочтение используется в новой сессии; чужая запись,
просроченная запись и внешняя инструкция не приобретают право управлять действиями.
Общая область `user_id="*"` рассматривается отдельно: в стенде она намеренно
используется для опыта с отравлением, а не как универсальный режим обмена памятью.

### 7. Идентичности и права доступа

Разобрать пользовательскую и сервисную идентичность, назначение токена и обмен
токенами на защищённом пути к АБС. Составить матрицу: кто, от чьего имени, к каким
данным и операциям обращается. Сравнить `ABS_MCP_MODE=secure` и `vulnerable`.

**Проверка:** чужой `customer_id`, неверные `azp` и `aud`, истёкший токен и токен
другой системы не дают доступа. Замена идентификатора в тексте или памяти не меняет
субъекта защищённой операции. Тревел-системе для проверки бюджета передаётся только
согласованный минимум, например решение о допустимости суммы, а не выписка по счетам.
Сам такой метод проверки бюджета студентам ещё предстоит реализовать.

### 8. Делегирование и согласование действий

Спроектировать состояния «запрошен поиск → получены варианты → выбран вариант →
подтверждена имитация бронирования». Денежное действие имеет отдельную ветвь
подготовки и подтверждения с проверкой суммы, валюты, получателя и срока полномочия.
Запрос «подбери» не разрешает «оплати».

Исходная имитация бронирования принимает идентификатор варианта, но не проверяет
его по сохранённой выдаче. Добавить эту связь и проверку владельца выбора.
Согласовать отказ банка и повторный подбор более дешёвого варианта с ограничением
числа попыток. Обратный API тревел-агент → банк не предоставляется автоматически:
можно оставить координацию банку либо отдельно спроектировать узкий интерфейс.

**Проверка:** поддельный или устаревший вариант отклоняется, изменение цены требует
пересогласования, полномочие поиска не позволяет исполнить платёж. Реальных заказов
и платежей внешнему тревел-провайдеру в задании нет.

### 9. Внешние данные и отравление памяти

Повторить [опыт с моком авиабилетов](EXPERIMENTS.md#memory-poisoning-через-минимальный-flights-mcp).
В учебном `.env` установить `MEMORY_ORCHESTRATION_INTERVAL_SECONDS=0`, чтобы обработка
не началась до измерения исходного состояния. Поместить материал в очередь и вызвать
операторский `POST /api/v1/orchestrator/collect` для нужного `conversation_id`.
Порядок авторизации описан в [настройках](CONFIGURATION.md#обработка-долговременной-памяти).

Проследить цепочку: ответ MCP → A2A → рабочая запись → решение оркестратора →
долговременная запись → последующее извлечение → ответ или попытка действия.
Сравнить исходный вариант с защитой происхождения, области использования и полномочий.
В текущей реализации этот опыт затрагивает память банка. Перенос между собственной
памятью тревел-агента и банка требует решения задания 6.

**Проверка:** отдельно измеряются попадание текста в память, его извлечение,
влияние на ответ и попытка привилегированного действия. Отсутствие записи может быть
корректным отказом оркестратора; наличие маркера ещё не доказывает успешную атаку.
Защита должна сохранять обработку допустимых запросов.

### 10. Отказы, повторы и восстановление

Смоделировать тайм-аут партнёра, недоступность памяти, повтор сообщения, изменение
схемы и разрыв соединения после выполнения операции. Задать правила повторов,
идемпотентности, проверки результата и обработки устаревшего состояния.
Различить «результатов нет», «источник недоступен» и «результат операции неизвестен».

**Проверка:** повтор не создаёт двойное списание или две логические брони; поиск
не подменяется моком при отказе Туту; ошибка связи не трактуется как разрешение
действия. Финансовые проверки выполняются только на локальных тестовых счетах.

### 11. Замена компонентов и сопровождение контрактов

Команды обмениваются реализациями банка и тревел-агента. Проверяются сочетания
«банк A / тревел A», «банк A / тревел B», «банк B / тревел A», «банк B / тревел B».
Менять внутренний код партнёра для каждой пары нельзя; допустимые адаптеры и точки
конфигурации заранее включаются в профиль взаимодействия.

Отдельно заменить MCP-провайдера или модель на совместимом API. Если требуется новый
SDK или другой API, явно учитывать отдельный адаптер. Совместимость интерфейса модели
не означает равенства качества ответов. Для несовместимого изменения контракта
описать версию, период перехода, ответственного и способ отката.

**Проверка:** все пары проходят один опубликованный набор проверок; отдельно
фиксируются протокольные, семантические, политические и модельные ошибки.
Изменение модели не должно отключать подтверждение или проверку прав.

### 12. Итоговый эксперимент

Другая команда или преподаватель предоставляет незнакомую реализацию одного
участника и набор обычных, ошибочных и атакующих сценариев. Студенты предъявляют
профиль взаимодействия, изменения кода, тесты и отчёт, позволяющий повторить результат.

В Langfuse сохраняются три независимых проекта. Связь восстанавливается по
идентификатору диалога и происхождению записей, без объединения всех систем в одну
родительскую трассу. Для причинной цепочки нужно явно связать запрос, результат,
задание оркестратора и запись памяти. Совпадение `session_id` показывает связь
сеанса, но само по себе не доказывает причину изменения поведения.

**Проверка:** защитить конкретное утверждение, например «смена тревел-агента
сохраняет смысл цены и изоляцию сессий», результатами всех соответствующих сценариев.
Отрицательный результат и ограничения измерения входят в отчёт.

## Измерения и оценивание

Для каждого результата сохраняются исходные количества и условия прогона.
Показатели считаются отдельно для обычных запросов, ошибок и атак.

| Показатель | Что считать |
|---|---|
| Успех задачи | Успешно завершённые допустимые сценарии / все допустимые сценарии |
| Соответствие контракту | Пройденные проверки схем, семантики операций и ожидаемых отказов / все такие проверки |
| Сохранение смысла | Число и типы ошибок валюты, стоимости, времени, маршрута и области данных |
| Контекст | Успешные продолжения диалога; случаи смешения пользователей или сессий |
| Полномочия | Попытки и исполнения неразрешённых действий; случаи раскрытия контрольных данных |
| Отравление памяти | Записи, извлечения, влияния на ответ и действия / соответствующие попытки каждого этапа |
| Восстановление | Успешные восстановления / внесённые отказы; число дублированных эффектов |
| Заменяемость | Пройденные пары реализаций; число, объём и время необходимых изменений |
| Затраты | Задержка, число LLM- и сетевых вызовов; стоимость при наличии достоверных данных провайдера |

Если попыток определённого вида не было, результат отмечается «не измерено».
Отсутствие неразрешённых действий проверяется вместе с успехом обычных запросов:
реализация, отклоняющая всё, не проходит курс. Для LLM-этапов нужны повторные прогоны
и распределение результатов; одна удачная демонстрация недостаточна.

Предлагаемая оценка: контракты и семантика — 25%, контекст и память — 20%, полномочия
и доверие — 20%, замена компонентов и восстановление — 20%, воспроизводимость — 15%.
Критерии и обязательные проверки преподаватель фиксирует до итогового эксперимента.

## Что сдаёт команда

1. Профиль взаимодействия и схему границ с указанием владельцев данных и решений.
2. Схемы сообщений, словарь значений, модель состояний и матрицу полномочий.
3. Реализацию и набор позитивных и негативных тестов с фиксированными входными данными.
4. Матрицу сочетаний независимо разработанных участников.
5. Отчёт с количеством прогонов, ошибками, измерениями и ограничениями выводов.
6. Инструкцию воспроизведения: ревизия кода, версии контрактов, настройки без секретов,
   подготовка начального состояния, идентификаторы опытов и ссылки на трассы.

Перед каждым опытом фиксируется состояние памяти: повторный `collect` обрабатывает
ожидающие задания, не очищает память и не переигрывает завершённые задания.
Команда описывает, какие тестовые записи удаляет или создаёт заново. Сброс всей
базы не является обязательным способом подготовки каждого опыта.

## Подготовка стенда

Порядок запуска остаётся общим для всех занятий:

```bash
cp .env.example .env
# Укажите провайдера LLM и настройки опыта в .env.
docker compose --env-file .env up -d --build
```

Команда копирования нужна только при первом запуске; заполненный `.env` не заменяют
примером при переходе к следующему занятию. Режимы мока, уязвимой АБС и ручной
обработки памяти описаны в [конфигурации](CONFIGURATION.md).

Исходные автоматические проверки — в [руководстве](RUNBOOK.md#автоматические-проверки),
сетевая проверка — `python3 scripts/check_system_isolation.py` после запуска.
Существующие тесты помогают проверить исходную реализацию; они не заменяют
приёмочные сценарии курса и не доказывают совместимость со всеми реализациями MCP/A2A.
